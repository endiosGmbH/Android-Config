# OP-18233 — Bump Compose UI to 1.10.0

**Ticket:** https://endios.atlassian.net/browse/OP-18233
**Repo:** Android-Config (version catalogue only)

## Goal

Raise `version.compose_base` from 1.9.0 to 1.10.0 so an inert `ComposeView` stops
claiming keyboard focus it then refuses. Every consumer repo resolves Compose
through this catalogue, so the one-line change is the whole delivery.

## Why 1.10.0

1.10.0 is the first release whose `AndroidComposeView` overrides `addFocusables`
and drops itself when the focus owner reports no focusable content, gated on
`isBypassUnfocusableComposeViewEnabled` (default `true`). 1.11.0 carries the same
fix with a larger behaviour delta and no benefit here. 1.12.0 would force
compileSdk 37; we are on 36 and it stays there.

Verified against the released AARs rather than release notes: the override is
absent in 1.9.0 and present from 1.10.0, and the flag's default is `true` in the
disassembled static initialiser.

## Change

`version.compose_base` 1.9.0 -> 1.10.0. Nothing else.

`compose_material` (1.7.0) and `compose_material3` (1.4.0) stay pinned. AGP
8.11.2, Kotlin 2.2.0 and compileSdk 36 all clear 1.10.0's floor, so no build
tooling moves.

## compose-foundation is deliberately not touched here

compose-foundation is never declared as a dependency in this catalogue or in the
shared build scripts; it arrives transitively, pinned to 1.8.1 by
`compose_material3` 1.4.0. A ui-versus-foundation skew therefore already exists
today, and this bump widens it from one minor to two.

Closing it is **not** a catalogue line. A new `compose.foundation` entry would be
inert until every consumer repo declared it, and there is no `constraints`,
`resolutionStrategy` or `platform()` block anywhere in the shared scripts to force
it centrally. The real options are a new central constraint or adopting
compose-bom, and both move compose-foundation two minors on top of the ui bump —
more behaviour change, against a pre-existing condition that has caused no known
defect. It belongs in its own ticket with its own regression pass.

## Risk

The version number is not the risk; the behaviour flags are. Relative to 1.9.0,
1.10.0 turns eleven flags on and three off — five focus changes, two nested-scroll
and View-interop changes, one semantics change — which lands on `ComposeView`
inside Views, Compose inside scrolling Views, and keyboard/TalkBack/Switch Access
traversal. The flag table is on the ticket.

Every flag is a `public static` mutable field, so a single regression can be
pinned back to its 1.9.0 behaviour at application startup without reverting the
bump.

## Verification

- Foundation and the pinned widgets build and run against 1.10.0.
- An inert `ComposeView` no longer swallows forward Tab: focus moves past it.
- A `ComposeView` with focusable content keeps its existing Tab order.
- The focus fixes already merged into Foundation still behave as specified —
  the parent-painted focus indicator on toolbar controls and on the address-search
  clear button, the toolbar Tab reachability fix, the loading-scrim focus stop and
  its login-form follow-up, and the shared pager focus stop. All linked on the
  ticket.

Robolectric cannot observe the defect — its `FocusFinder` returns the correct next
view in both directions. Verification needs a real `ViewRootImpl` and injected key
events on a device.
