# Spec: Scan every Android pull request for secrets

**Ticket:** [ENB-1348](https://endios.atlassian.net/browse/ENB-1348)
**Created:** 2026-11-25
**Status:** Draft
**Repo:** Android-Config (Jenkins shared library `android-ci`: `vars/`, new `resources/`)

## Context

Every pull request in the Android repos must be scanned for credentials with gitleaks, as iOS
already does (OP-19425, `endiosGmbH/ios-ci`: `vars/iosPRVerify.groovy` stage `Secret scan`,
config `resources/eo-gitleaks.toml`). The repos still hold credentials that OP-18784 has not
removed yet, so the scan covers only what the pull request adds, never the whole history.

iOS lesson (ios-ci PR #9, "OP-19425 Secret scan: no token in git or argv", merged 2026-11-18):
the first version skipped silently when it could not resolve the base. The Android scan must fail
closed instead.

Out of scope (ticket): removing existing credentials (OP-18784), making the check required or
blocking merge (ENB-1350), history rewriting, token rotation.

- Today every Android PR shows exactly one status, `continuous-integration/jenkins/pr-merge`

## Requirements

### Functional
- `androidPRVerify` runs a gitleaks secret scan on every pull request build, before any Gradle work.
- The scan covers only what the PR adds relative to its base `origin/${CHANGE_TARGET}`: each PR
  commit, plus the net change the PR would make to the target (so a credential introduced while
  resolving a merge is caught too).
- A credential the PR adds makes the secret-scan check fail. The log names file, line and rule,
  never the value.
- Firebase `google-services.json` API keys are allowlisted. Any other credential in that file
  still fails.
- If the base cannot be determined (no `CHANGE_TARGET`, `origin/<target>` missing, or no merge
  base), the scan fails instead of skipping.

### Non-Functional
- Pinned gitleaks binary, verified by SHA-256 before it runs. No unpinned `brew install`.
- No credential is in scope while gitleaks runs, and no network fetch happens inside `sh`
  (`docs/android-ci.md` gotcha).
- The allowlist is central (Android-Config). A PR cannot silence its own finding with a
  repo-level `.gitleaksignore` or `.gitleaks.toml`.
- The extra time is a few seconds (a 1-commit scan takes under 0.1 s locally, plus one tarball
  download).

## Behaviors (TDD Plan)

Behaviors 1–6 map 1:1 to the Definition of Done. Behaviors 7–11 come from the ticket's scope
rules and from the design below. All of them are exercised by the local harness (see Technical
Notes → Tests) against throwaway git repos, with randomly generated fake credentials.

1. [x] (DoD 1) Given a PR whose commit adds a credential (e.g. a `github-pat`-shaped token in a
   `.kt` file), when the secret scan runs, then the scan exits non-zero and the secret-scan
   check **fails**.
2. [x] (DoD 2) Given that failing scan, when the build log is read, then it **names the file**
   (path:line).
3. [x] (DoD 2) And the build log **names the rule** (gitleaks `RuleID`, e.g. `github-pat`).
4. [x] (DoD 2) And the build log **never contains the value**: the fake token string does not
   appear anywhere in stdout/stderr.
5. [x] (DoD 3) Given a PR that **only changes `google-services.json`** (adding a Firebase API key
   to `app/google-services.json` or a flavor copy such as `app/src/debug/google-services.json`),
   when the scan runs, then it **passes**. Both `gcp-api-key` and `generic-api-key` are
   suppressed for that path. The local test showed that allowlisting `gcp-api-key` alone makes
   `generic-api-key` fire on `"current_key"`.
6. [x] (DoD 4) Given the scan **cannot find the PR's base branch** (`CHANGE_TARGET` unset or empty,
   or `origin/<CHANGE_TARGET>` does not resolve, or there is no merge base with `HEAD`), when the
   scan runs, then the check **fails instead of skipping**, with a message that names the
   missing ref. A missing argument (`GITLEAKS`, the config, the install dir) also exits 2
   (`error`), never 1 (`failure`).
7. [x] (gap: allowlist is narrow) Given a PR that adds a non-Firebase credential (e.g. a
   `github-pat`) inside a file named `google-services.json`, or a Firebase-shaped key in a `.kt`
   file, when the scan runs, then it fails.
8. [x] (scope: only new secrets) Given a credential that already exists on the target branch, and
   a PR that does not touch it, when the scan runs, then it passes.
9. [x] (scope: only new secrets) Given the target branch received a credential after the PR
   branched, and Jenkins built the PR as a merge commit (merge strategy, `HEAD^2` = target tip),
   when the scan runs, then it passes. The target's changes are not attributed to the PR. A plain
   `-m` scan (the iOS form) fails this case, as the local test showed. A PR built without a merge commit
   and behind its target is diffed against the merge base, so a credential the target removed
   later is not attributed to the PR either.
10. [x] (gap: history) Given a PR commit that adds a credential and a later PR commit that removes
    it, when the scan runs, then it fails. The credential would stay in history after a merge.
11. [x] (gap: merge resolution) Given a PR whose own merge commit introduces a credential while
    resolving a merge (it is in neither parent), when the scan runs, then it fails.
12. [x] (gap: bypass) Given a PR that adds a `.gitleaksignore` listing its own finding's
    fingerprint, when the scan runs, then it still fails. Locally, gitleaks 8.30.1 honours
    `.gitleaksignore` in the scanned directory even with `-i <other path>`, so the stage deletes
    the workspace copy before scanning.
13. [x] (gap: bypass) Given a PR that adds `*.kt -diff` or `*.kt binary` to `.gitattributes`
    together with a credential in a `.kt` file, when the scan runs, then it still fails and the
    log omits the value. Those attributes make `git log -p` print no patch, so gitleaks would see
    nothing. The script appends `* !diff` to `$(git rev-parse --git-path info/attributes)`, which
    outranks every in-tree `.gitattributes` (and works in worktrees). `!diff` (unspecified) rather
    than `diff` (forced text), so real binaries stay binary (behavior 18).
14. [x] (gap: rule) Given a PR that adds a `dir`-algorithm JWE (`eyJ…..iv.ciphertext.tag`, empty
    encrypted-key segment) to a `.kt` file, when the scan runs, then it fails with
    `endios-jwe-token`. The rule's second segment is `*`, not `+`.
15. [x] (status target) The `ci/jenkins: secret-scan` status goes to the PR head on GitHub.
    `eo-secret-scan.sh post-status` posts to `HEAD` first. If GitHub answers 422 with "No commit
    found" (the commit is not on GitHub, so it is a Jenkins-local merge) and `HEAD` has two
    parents, it posts to `HEAD^1`. Any other 422 (e.g. the status limit) only warns. The first successful post stores the SHA in `.eo-secret-scan.sha`, so the later
    `failure`/`success` lands on the same commit; `pending` forgets a previous build's SHA.
    Covered against a local fake statuses API: Jenkins merge (`HEAD` unknown) → `HEAD^1` for both
    posts; a 422 with another message → no fallback, warning only; an author merge with a forged Jenkins identity (`HEAD` known) → `HEAD`; a linear PR →
    `HEAD`; a stale SHA file is ignored on `pending`; an API error only warns (exit 0), and the
    log never holds the token. The earlier identity test (`nobody@nowhere`) let an author forge it.
16. [x] (robustness: stalled GitHub) Given GitHub accepts the connection but never answers,
    when the gitleaks download runs, then it gives up (`--connect-timeout 10 --max-time 120`)
    and the scan exits 2 (`error` status), instead of the pipeline's 45-minute timeout aborting
    the consumer build (`catchInterruptions: false` passes timeouts through). A status post is
    bounded the same way (`--max-time 20`) and only warns. Covered with a local silent listener
    and a shortened `--max-time` (`EO_DOWNLOAD_MAX_TIME`, `EO_STATUS_MAX_TIME`).
17. [ ] (scope: every repo) Given any of the 65 consumers of `androidPRVerify`, when it builds a
    PR after this change merges to Android-Config `develop`, then the `Secret scan` stage runs.
    No consumer change is needed. This is verified manually (QA), after the merge to `develop`.
18. [x] (false positives: binaries) Given a PR that adds a binary (for example
    `gradle-wrapper.jar`) whose bytes contain a key-shaped run, when the scan runs, then it
    passes. Git's binary detection still applies, so gitleaks never sees compressed bytes as a
    patch (forcing `diff` would, and `generic-api-key` would flag them).

## Technical Notes

### Decisions (recommendation + reason)

**D1: Getting gitleaks onto the agent: pinned release tarball + SHA-256.** Download
`gitleaks_8.30.1_darwin_arm64.tar.gz` from `github.com/gitleaks/gitleaks/releases`, check it
with `shasum -a 256 -c`, and extract it into the workspace. ktlint is downloaded the same way,
but ktlint has no checksum. Pick the tarball by `uname -m` (`arm64` → `darwin_arm64`,
`x86_64` → `darwin_x64`), and fail on any other arch. **Decided (user, 2026-11-25):** the agent may be
macOS arm64 or x64; any other OS or arch fails clearly. The agents are macOS (homebrew paths in
`environment`). Version and checksums are constants in the library, not overridable, because
a checksum belongs to its version. Values from `gitleaks_8.30.1_checksums.txt`:
- `darwin_arm64`: `b40ab0ae55c505963e365f271a8d3846efbc170aa17f2607f13df610a9aeb6a5`
- `darwin_x64`: `dfe101a4db2255fc85120ac7f3d25e4342c3c20cf749f2c20a18081af1952709`

v8.30.1 is the latest release (2026-03-21), and it is the version the local harness runs.
Rejected: `brew install gitleaks` as iOS does (unpinned, and it changes the agent); Docker
(not used on these macOS agents).

**D2: Diff range: the PR's own commits plus the PR's net diff, base from `env.CHANGE_TARGET`.**
- Base: `CHANGE_TARGET` only. If it is empty, fail. The stage does **not** fall back to
  `cfg.baseBranch`, unlike the changeset logic. It uses `origin/${CHANGE_TARGET}`, which the
  branch source has already fetched (no fetch in `sh`). It fails if
  `git rev-parse --verify origin/<target>` or `git merge-base origin/<target> HEAD` fails.
- Synthetic net-diff commit:
  `NET=$(git commit-tree HEAD^{tree} -p origin/<target> -m …)`, with a throwaway identity set
  through env. Its diff is exactly what the PR would change on the target. That includes any
  merge-resolution content, and none of the target's own changes.
- In-tree diff attributes are reset: the script appends `* !diff` to `$GIT_DIR/info/attributes`
  (via `git rev-parse --git-path`), so a PR's own `-diff`/`binary` in `.gitattributes` cannot hide
  its patches from gitleaks (behavior 13), while real binaries stay binary (behavior 18).
- Scan: `gitleaks git --log-opts="^origin/<target> HEAD $NET"`, without `-m`. PR commits are
  scanned one by one (catches add-then-remove). Merge commits produce no patch (no false
  positives from the target, nor from the merge commit Jenkins creates). `$NET` catches content
  introduced by a merge resolution.
- Why not the iOS `-m <merge base>..HEAD`: Android uses the "merge with target" PR strategy.
  The local test showed that `-m` attributes the target's newer changes to the Jenkins merge
  commit (a false positive on every behind-target PR once a flagged credential lands in
  `develop`). `--cc` was tested too: gitleaks finds nothing in combined diffs.

**D3: Redaction and report format.** Use `--redact --no-banner --no-color`, without `-v`. With
`-v`, gitleaks prints the surrounding `Finding:` context line and the author email. Report:
`--report-format template --report-template <temp file> --report-path -` with
`{{range .}}{{.File}}:{{.StartLine}} {{.RuleID}}{{"\n"}}{{end}}` (the script writes it to a
temp file), so each finding prints as
`path:line rule`. Commit SHAs are left out, because the `$NET` SHA is synthetic. The stage
also echoes a fixed hint (inspect locally with `gitleaks git --redact`).

**D4: Allowlist config: central `resources/eo-gitleaks.toml` in Android-Config.** It is loaded
with `libraryResource('eo-gitleaks.toml')` and written to the workspace as `.eo-gitleaks.toml`,
exactly as iOS does. It starts as a copy of the iOS file: `[extend] useDefault = true`, plus
rules `endios-jwe-token` and `hardcoded-authorization-header`, because the Android repos hold
the same backend tokens (OP-18784). It keeps the iOS false-positive allowlists only where they
apply. Add:
```toml
[[allowlists]]
description = "Firebase google-services.json: the Android API key is public by design"
targetRules = ["gcp-api-key", "generic-api-key"]
paths = ['''(?:^|/)google-services\.json$''']
```
The allowlist is path-based and rule-targeted: a regex on the key alone would also allowlist
Firebase-shaped keys pasted into code. iOS has no Firebase entry (its plist was not flagged),
so the iOS part this mirrors is the `[[allowlists]]` + `targetRules` form. Per-repo
`.gitleaks.toml` is rejected: the PR under scan could allowlist itself. The stage runs
`rm -f .gitleaksignore` and passes `--ignore-gitleaks-allow`, so inline `gitleaks:allow`
comments cannot bypass the scan either. **Decided (user, 2026-11-25):** keep
`--ignore-gitleaks-allow`; every exception goes through the shared `resources/eo-gitleaks.toml`.

**D5: Stage placement and what appears on PRs.** A new stage `Secret scan` comes directly after
`Checkout & Changeset` and before `ktlint`. It reports the check context `ci/jenkins: secret-scan`
(byte-identical to iOS). **Decided (user, 2026-11-25):**
- **Non-blocking, with its own status.** The stage fails itself but not the build:
  `catchError(buildResult: 'SUCCESS', stageResult: 'FAILURE', catchInterruptions: false)`, so an
  abort or timeout still stops the build. Making the scan blocking is ENB-1350.
- The stage posts a GitHub commit status `ci/jenkins: secret-scan` through the statuses API, as
  iOS `ghStatus()` does, with credential `GITHUB_TOKEN_ENDIOSONEGITHUB` (token on curl's stdin,
  never in argv): `pending` at the start, then `success` (exit 0), `failure` (credentials found,
  exit 1) or `error` (the scan could not run: missing base branch, install failure; exit 2). A
  missing base therefore never posts success. The description is a fixed string, never a value.
- The status goes to the PR head, so it shows on the PR. `eo-secret-scan.sh post-status`
  picks it (behavior 15) by asking GitHub, not by the merge commit's shape or identity: `HEAD`,
  and on a 422 "No commit found" for a two-parent `HEAD`, `HEAD^1` (other 422s only warn). **Decided (2026-11-25):** existence check. A
  shape test (`HEAD^2 == origin/<target>`) misread an author's own merge head and a Jenkins merge
  whose target moved on; an identity test (committer `nobody@nowhere`) could be forged by an
  author. The token reaches the script on stdin, never argv. The credential was verified on real
  Jenkins 2026-11-25 (throwaway PR endiosOneSampleWidget #30). A failure to post (missing
  credential, API error, timeout) only logs a warning and never fails the stage or the build.
  gitleaks runs outside `withCredentials`.

**D6: Tests.** Android-Config has no Jenkins pipeline unit tests and no CI. Move the scan's shell
into `resources/eo-secret-scan.sh` (arguments: target ref; it uses `$GITLEAKS`, the config path
and the template path). The stage runs it with `libraryResource` + `sh`. A local harness
`test/secret-scan/run.sh` builds throwaway repos in `mktemp -d`, using random fake tokens
generated at runtime (never committed). It runs the **same script** for behaviors 1–16 and
asserts the exit code and the log content (value absent). Jenkins ignores `test/`. Behaviors
1–16 are cases `b1_*` … `b16_*`; D1 is covered by `install_*` (real pinned download, wrong OS,
wrong arch, checksum mismatch). `jenkins_merge` only creates a merge commit when the PR is
behind its target, so most cases build without one. Behaviors 1, 5, 10 and 13 also run as
`*_merge_build_*` variants: the target moves first, then a Jenkins-style merge (`HEAD^2` =
target tip, asserted). Behavior 9 and the behavior 15 Jenkins-merge case are merge builds too.
Behavior 15 posts to a local fake statuses API (python3 `http.server`) with a dummy token;
behavior 16 uses a local listener that never answers. Behaviors 7, 8, 10 and 11 were green on
arrival; each was shown to go red against a mutated script or config (too-broad allowlist, iOS
`-m` form, no net commit, net commit only); the merge-build variants likewise (no forced diffs,
net commit only). Behavior 4 was green on arrival too (`--redact` from the first commit); it was not
mutation-checked, because an unredacted run is off-limits. The Groovy
wiring (stage order, `catchError`, context name) is verified by the manual QA PR.

### Files
- `vars/androidPRVerify.groovy`: new `Secret scan` stage, `secretScanStatus` helper, KDoc
  update, and `post.always` cleanup of `gitleaks`, `gitleaks_*.tar.gz`, `.eo-gitleaks.toml`,
  `.eo-secret-scan.sh` and `.eo-secret-scan.sha`.
- `resources/eo-gitleaks.toml` (new), `resources/eo-secret-scan.sh` (new; it also holds the
  report template, so there is no separate `.tmpl` file).
- `test/secret-scan/run.sh` (new).
- `docs/android-ci.md`: contents list, the scan, and how to run it locally.

### Known gaps
- A token added by an evil merge (in neither parent) and removed in a later commit is not seen:
  the net diff no longer has it, and merge commits get no patch (`--remerge-diff` needs git ≥2.36).
- gitleaks' default global path allowlist skips files such as `*.svg`, `*.png` and `node_modules/`.
- UTF-16 text files are not scanned (git treats them as binary).
- Run locally in a linked worktree, the `* !diff` line lands in the main clone's common git dir
  (`info/attributes`); harmless on Jenkins, which has no linked worktrees.

### Constraints
- Changes to `vars/` reach all 65 consumers as soon as they merge to `develop`. Test first with
  `@Library('android-ci@feature/ENB-1348')` from one consumer (QA).
- No ticket IDs in code comments, and comments are at most 2 lines (repo conventions).

## QA

**Recommended app:** _none: CI-only change, no QA app applies_

**Manual verification instead:** in one consumer (suggested: endiosOneSampleWidget-Android,
low traffic), open a throwaway **draft** PR whose `Jenkinsfile.prverify` pins
`@Library('android-ci@feature/ENB-1348') _`, and push in sequence:
1. a commit adding a fake `ghp_…` token in a `.kt` file → `Secret scan` is red; the log shows
   `path:line github-pat` and no value.
2. every PR commit is scanned, so a revert on the same branch stays red (behavior 10). Push a
   **fresh branch from `develop`** (same `@Library` pin) whose only change is
   `app/google-services.json` → green.
3. DoD 4 (missing base) cannot be triggered from a real PR build, where Jenkins always sets
   `CHANGE_TARGET`. Behavior 6 in the harness covers it.

Then close the PR and delete the branch. Do not merge it.
